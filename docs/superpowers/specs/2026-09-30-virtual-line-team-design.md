# 虚拟产线停复机与五人维修小组设计

日期：2026-09-30

## 目标与边界

当前系统只有一条**虚拟**产线。监控确认设备故障时，停止整条产线；故障维修工单由系统自动派发；登录的被派工维修人员确认完成后，系统在核对整线条件后启动并验证恢复。系统不得把测试或前端提交的数据当作真实恢复证据，也不得连接真实 PLC。

小组固定五个席位：一名监督人、四名维修人员。监督人只查看派工与接单状态并进行站内催办，不审批派工、不确认维修、不控制产线。注册开放给使用该本地虚拟工厂的人员；注册时填写用户名、密码、身份，维修人员还需选择主要负责设备。设备归属是派工偏好，不是唯一资格限制。

## 现状与方案选择

- Backend 已有 MySQL 工单持久化，但没有个人账号或登录会话。
- Agent 侧派工候选人仍是固定演示技师；前端维修确认可提交任意姓名和恢复样本。
- Monitor 可查询设备、读取快照，并向虚拟工厂发单设备控制命令；目前没有整线控制 API，监控结果也未自动控制设备。

选择 **Backend 作为账号、会话、工单和控制记录的数据源**；Agent 负责监控、诊断、派工决策与虚拟设备控制，前端通过现有同源入口访问。没有选择 Agent 独立管理账号，因为会让工单与身份分属两处；没有选择仅前端保存身份，因为无法可信地确认维修和复机。

## 账号与权限

1. Backend 增量创建账号、会话与站内催办记录。账号至少保存内部 ID、唯一用户名、加盐密码哈希、身份、主要负责设备 ID、启用状态及审计时间；不保存明文密码。身份只允许 `supervisor` 与 `technician`，监督人没有负责设备。注册时从虚拟工厂当前设备目录选择设备 ID，不能以任意文本伪造设备归属。
2. 注册身份由用户选择，但在 MySQL 事务中原子限制监督人最多一名、维修人员最多四名；并发注册不能突破席位数。重复用户名、无效身份、无效设备或名额已满时明确拒绝，不覆盖已有账号。密码和会话凭证不写入日志、工单或 Agent 上下文。
3. 登录使用 Backend 签发的服务端会话；浏览器持有 `HttpOnly`、同源限制的会话 Cookie。注销使会话失效。Agent 对人工工单动作向 Backend 验证会话与身份，不能信任客户端提交的 `maintenance_confirmed_by`、`assignee`、角色或代理附加的普通请求头。Agent 的内部服务令牌与人的会话分离。
4. 维修人员只可为本人被派工的工单提交维修反馈及完成确认。监督人可查看全部派工和接单状态、针对具体工单创建站内催办；不能完成工单或触发复机。催办保存工单 ID、发送者、接收者、时间及阅读状态，维修人员登录后可查看。
5. 公开自选监督人身份有首位注册者占用监督席位的风险，因此此方案仅适用于当前本地虚拟工厂；不得将它描述为可直接用于生产。未来接真实设备前必须改为受控授权。其他服务和普通页面不因新增个人账号而获得额外控制权限。

## 自动派工

1. Agent 的候选人来自 Backend 的已启用、已注册维修人员，不再使用固定 `TECH-*` 名单作为正式派工结果。对既有演示适配器可保留明确标记的测试用途，但生产查询不能混入演示人员。
2. 系统优先选择主要负责故障设备的维修人员；若其不可接单，则在同组其他维修人员中按未完成工单数最少选择，平局使用稳定的账号 ID 顺序。不能从未注册人员、监督人或不可用账号中选人；不能编造技能、班次或可用性。
3. 派工写入真实账号 ID、显示用户名、故障设备、工单与派工原因；同一故障事件和同一工单的重复执行应幂等。没有可派人员或 Backend 不可用时保留“待派工”，显示原因并供监督人催办，不伪造已派工状态。原有工单继续可见，不能删除或自动改写。

## 整线停机

1. 只对监控明确确认的故障事件触发停机，不把普通预警、未知数据或单纯失联直接冒充已确认故障；沿用现有监控分类，工业阈值不由本功能猜测。一次故障事件生成稳定的控制操作 ID，并记录设备目录、逐设备命令和返回结果。
2. 单条虚拟产线由虚拟工厂设备目录中的所有设备组成。确认故障后 Agent 对目录内每台设备发送 `emergency_stop`，随后读取各设备状态验证。Monitor 控制端只接受已确认的虚拟工厂适配器，不通过此功能接入真实 PLC。
3. 同一故障重复轮询不得重复下发停机；多个设备故障合并为同一次持续停机状态，但分别保留故障事件和工单。控制调用超时后先查询设备实际状态，不能盲目重试写操作。若任何设备未确认停机，整体状态为“部分停机失败”，逐设备展示原因并记录审计，不能显示为整线已安全停止。
4. 停机决策不能依赖 MySQL 正常才能执行：持久化或派工暂时失败时，仍尝试停机，并把未持久化/待对账状态明确暴露。故障事件 ID 必须能由原始监控事件稳定重建；数据库恢复后先读取各设备状态，再按事件 ID 对账，不能因为进程重启而盲目重发控制命令。审计记录未恢复前禁止自动复机。

## 工单确认与复机

1. 被派工维修人员登录后提交维修反馈并明确确认完成。Backend/Agent 使用服务端验证的账号 ID 记载确认人。原有仅含前端姓名、`passed=true`、`restart_requested=true` 或前端样本的记录，不自动获得复机资格。
2. 整线复机门禁要求：本次停机涉及的所有已确认故障都已处理；对应维修工单完成且由其被派工维修人员确认；没有其他未完成的故障工单；虚拟工厂当前目录和各设备状态可读取、设备归属匹配、样本时间满足现有 `RECOVERY_MAX_AGE_SECONDS` 新鲜度配置、无仍存在的故障证据。`emergency_stop` 本身是停机控制状态，不能单独作为“维修未完成”的证据；但其他故障或安全互锁仍须阻止复机。缺失、过期或设备不符一律阻止复机并显示具体原因。
3. 门禁满足后，Agent 对整线逐台发送 `start` 并读取新的设备快照。只有所有设备都实际进入正常运行、无新故障，才显示“恢复运行”。启动中、状态不可知或部分设备启动失败时不作成功宣告；对已启动设备执行安全回停并记录逐台结果。故障重现时重新停止整线，保留或重开相应故障处理，不能仅靠一次 `passed=true` 关闭流程。
4. 停机和复机都是有状态、幂等的服务端操作：同一操作 ID 不重复执行；参数变化生成新操作并重新评估门禁；超时属于结果不确定，先读回设备状态再对账。监督人催办不影响复机门禁。任何数据库、身份或虚拟工厂证据不足均使复机失败关闭，但不屏蔽已确认故障的停机尝试。

## 接口与前端范围

- Backend 提供注册、登录、注销、当前身份、维修人员候选、站内催办、控制事件写入/查询和会话校验接口；只对必要的人机接口开放浏览器访问，内部工具端点继续隔离。Monitor 的同源代理明确列出允许路径和方法，并正确转发/校验 Cookie；服务间调用使用独立凭证。Agent 的人工工单操作需要由 Backend 校验会话，自动监控/派工则继续通过独立的服务身份执行。
- Agent 既有监控入口继续展示虚拟产线，新增整线状态、逐台控制结果及未解决故障；工单页面增加登录、注册、本人任务和维修确认；监督人页面展示派工、接单与催办。界面只显示后端真实状态，不以按钮点击即视为设备启动成功。
- 注册时的“主要负责机器”用于派工优先级；其他维修人员仍可承接同组工单。前端改动限于这些必要交互，不重做其他页面。

## 数据迁移与验证

数据库采用增量迁移，新表及索引不删除旧工单和历史数据。旧工单仍可查询；若未绑定已注册维修人员，应明确显示身份未验证，不能作为自动复机依据。迁移前先备份将修改的源码及数据结构，提供恢复步骤；不修改生产环境配置，不自动清除数据。

先补失败回归测试，再实现：注册唯一性与并发席位、哈希和会话、角色越权、设备归属与派工回退、零候选人、监督催办、故障整线停机与幂等、多故障阻止复机、伪造前端确认、过期/错设备快照、部分停机/启动失败、超时对账、重启后状态恢复。使用隔离数据库和虚拟工厂测试适配器，不调用真实设备或收费模型。依次跑 Backend 与 Agent 定向测试、前端测试、跨服务契约测试；MySQL 或虚拟工厂不可用时将集成受阻与业务测试失败分开报告。离线通过不等于真实设备生产验收。

## 验收标准

- 五个席位规则真实落在 MySQL；登录身份决定人工工单权限，密码不以明文存储或出现在日志中。
- 故障工单优先派给设备负责人，必要时派给同组其他维修人员；监督人可看到具体派工与催办记录。
- 单设备确认故障即触发整条虚拟产线停机，逐台结果可核对；同一事件不重复写控制命令。
- 只有全部相关故障工单由被派工维修人员确认完成且服务端读取的整线状态满足条件，才尝试启动；未验证时保持停止或明确标为状态未知。
- 仅所有设备复机后的真实快照均正常，界面才显示“恢复运行”；任何失败都保留可追踪原因。
