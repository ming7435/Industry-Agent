# 失败任务只读记录与服务异常兜底

## 目标与范围

删除网页“从失败步骤继续”及对应公开执行接口，保留已失败任务、步骤和审计。服务异常或业务证据不足不再只有孤立错误：生成服务器持久化的异常核查待办，关联原任务、Trace、设备或零件、已知故障、服务异常原因及已完成阶段。允许有权限维修人员填写实际处理反馈并汇总异常处理报告。

这是人工处理闭环，不能将异常接管等同维修完成或设备恢复。没有维修方案时工单页显示“异常核查待办”，不是伪造 WO/维修方案，不能拆修、启停设备或放行质检。正式维修、审批、恢复核验、人员资格、公差与 CAD 实体校验保持原约束。无人确认时保持待人工处理。

## 数据与接口

复用已有 MySQL JSON 持久化适配器；显式隔离测试可使用临时存储。以原恢复记录编号生成稳定 EXC 编号，按任务幂等，存服务器验证的标量事实，不保存原 context、密钥或请求身份。记录和异常报告同一数据源，不需要其它失败服务可用才能读取。

新增 ServiceExceptionCases.record(checkpoint)、list/get、handle(case_id,feedback,actor)、report(case_id)。处理状态 awaiting_manual → handled；这是异常已人工接管，不代表原业务阶段成功。结果未知的原操作仍未知，不重放动作。原 failed/blocked/timeout 断点不改为 completed。

新记录由 RecoveryManager.checkpoint 的终态边界收集；服务启动时对旧失败记录做有界回填，只生成新记录，不重跑 Agent、工具或故障。正常运行、已完成、正常等待审批/人员、无需维修和只读权限拒绝不能制造服务异常。

GET /api/runtime/recovery 仅返回授权的只读失败摘要；POST resume 移除。GET /api/runtime/service-exceptions、POST /{case_id}/feedback、GET /{case_id}/report 复用服务端 Team 会话与同源限制。监督人只查看，维修人员仅处理本人/负责设备的记录。反馈只接受 request_id、feedback，不接受执行状态、passed、actor_id 或方案。请求参数不一致不能复用幂等回执。

报告为已有 incident_report 契约，明确 scope=service_exception_record、来源失败任务及人工反馈，不生成未知根因/维修步骤/检测值。EXR 报告读取和 PDF 生成走真实文件工具，并核对同一身份权限。正常报告服务不被替换；数据库不可用明确失败，不伪造已保存。

## 前端

失败任务面板改为“失败任务记录”，仅刷新与查看，无续跑、恢复次数操作或 mutation。新异常待办在相关业务中心独立显示：故障相关待办关联诊断、维修方案、工单、报告；独立知识问答/质检/CAD 记录只显示在本领域、日志和报告，不能为无设备故障的问答派维修工单。

页面标明服务异常原因、当前已知故障、未生成的业务结果、原任务编号、关联真实工单（若存在），允许授权维修人员提交非空处理反馈。报告可查看、生成 PDF、打开下载。旧接口读失败、账号切换和慢响应不能串数据、重试写入或重复执行旧任务。

## 验证与边界

测试真实 Case/Recovery/API/PDF 函数及真实浏览器，仅替换外部服务。覆盖故障关联、所有实际 Agent 失败类别、独立质检/问答隔离、重复/并发反馈、越权及 CSRF、敏感数据、DB 不可用、未知副作用和原失败状态保持。无真实设备或收费模型联调，不自动部署，不删除数据或覆盖其它工作。

历史内部断点对账兼容实现保留以免破坏旧数据和审批完整性，但不再通过公开失败续跑接口或前端调度。此轮不将服务异常人工作业变成正式维修方案自动批准。
