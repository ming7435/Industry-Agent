# Agent 节点、状态、工具与 Skill 精简设计

日期：2026-10-03。对象：当前本地 `L:/industry_agent`，以磁盘中的源码为依据。

## 1. 已确认的目标与边界

用户已确认“功能不变、实现精简”的范围：整理现有节点、状态、Tool 和 Skill，合并重复实现，删除经调用链与测试证实无用的代码。

保留五服务架构与九个业务 Agent；不重做前端，不调整模型供应商，不修改生产配置，不操作业务数据库，不调用真实设备控制接口。现有工单、质检、报告、知识问答、审批和日志功能均保留。Skill 继续使用 Markdown 与 YAML Front Matter，不改回独立 YAML 文件。

“调用次数少”只用来寻找候选项，不能证明代码无用。审批、失败回退、复检、幂等对账、故障恢复和安全门禁即使低频，也不能据此删除。

当前工作区包含上一轮维修团队和虚拟产线控制的未提交修改。本轮以这些修改后的文件为起点，不回退、不覆盖，也不把尚未完成的功能当作冗余。

## 2. 当前结构与实际冗余

正式入口为 `AgentOrchestrator → LangGraph(runtime) → RuntimeNode → RuntimeCoordinator`；由 Planner、Policy、Dispatcher、ExecutionManager 和各 Agent 的领域 Graph 完成业务。顶层 Graph 已经只有一个节点，不再继续压缩。

静态梳理得到九个领域 Graph 共 96 个注册节点、ToolRegistry 共 66 个处理器、Skill 目录共 32 份 Markdown。这些是源码数量，不是线上调用频率；也不能据此判断执行开销。

| 类别 | 已核实的情况 | 处理方式 |
| --- | --- | --- |
| 节点 | 九个领域 Graph 都分别注册初始化与 Skill 加载 | 合并图中的准备阶段，保留原有条件分支和真实子步骤日志 |
| 节点 | Quality 的 `decision` 只返回 `route=final`，判定已由 `validate_part` 完成 | 删除空跳转节点，将验收结果直接交给 `final` |
| 节点 | Maintenance 的 `fallback` 注册后没有任何入边 | 核对 Agent 外层异常处理后移除无入口的图注册；只有函数也无调用时才删除函数 |
| 旧编排 | `graph/nodes.py` 的 OrchestratorNodes 不进入正式 Graph，但仍被六组历史测试导入 | 先把业务断言迁移到正式 Runtime，再删除旧业务编排实现；不删除测试场景 |
| 状态 | 多个 TypedDict 重复声明执行身份、Skill 与步骤轨迹字段 | 提取一个公共 TypedDict，仅继承相同字段，领域字段留在各自状态中 |
| 状态 | `rework_via` 在 Agent 源码中仅有声明 | 核对响应与共享契约后移除无用声明；不改变质检整改业务状态 |
| 工具 | `query_stock` 直接转调 `query_inventory` | 合并实现，保留两个可调用名称及原返回结构 |
| 工具 | 库存、RAG 和 CAD 存在多份薄封装 | 共用查询实现；保留不同过滤条件、精确匹配规则和结果投影 |
| Skill | CAD 图纸定位与部件查询触发规则、工具集合相同；Router 两份定义均默认激活且无工具 | 合并重复文档与步骤声明，保留旧名称解析和业务说明 |

以下内容并不等价，不能简单合并：工单创建与更新、反馈与完成、关闭与重开；质检通过与未检测/数据不足；经验检索与写入；报警检索与手册检索；库存事实与可用性判断；诊断的 Tool Guard 与 Loop Guard。

## 3. 方案选择

采用“内部实现收敛、外部契约兼容”的方案。它减少重复代码和无业务意义的图节点，同时保留已有 API、工具名称、审批边界和历史数据。

不采用把九个 Agent 合成少数大 Agent 的方案：这会改变职责与调度接口，也不符合本轮仅精简现有实现的目标。

不采用按历史调用量批量删除工具或 Skill 的方案：目前没有足够的完整调用统计，且低频分支可能正是异常处理与安全边界。

## 4. 节点与数据流

### 4.1 准备阶段

每个领域 Graph 的 `initialize → load_skill` 收敛为一个准备节点。输入归一化仍先于 Skill 选择。原初始化返回失败或阻断时，不运行后续 Skill 选择；不得因合并而放行无效输入。

公共帮助函数仅负责组合准备步骤，不引入第二套调度器、插件引擎或通用业务框架。Diagnosis 等领域仍保留自己的解析和策略。

真实执行的输入归一化和 Skill 选择各自保留日志，使用原 task_id、trace_id、Agent 和 Skill 身份。减少的是图调度节点，不是用户所需的执行明细。

### 4.2 业务节点

Quality 保留尺寸、外观、材料、功能与工艺五项检测以及身份、规格、汇总验证；只去掉没有判定逻辑的 `decision` 图节点。

Maintenance 无入边的 fallback 只在确认不存在独立调用后删除。外部异常兜底、证据不足与不可派工结果仍须存在，不能以“没有图入边”为理由删除异常处理。

旧 OrchestratorNodes 迁移必须先保留原测试的业务断言：诊断低置信度不得派工、证据不足阻断、无维修必要不创建、维修后才学习和生成闭环报告。新的测试直接调用正式 Runtime 或实际 API，不能仅检查源码文本，也不能 mock 掉被测编排逻辑。

## 5. 状态收敛

公共执行状态只统一相同的类型声明，例如 active_agent、active_skills、current_step 与轨迹字段；各 Agent 的请求、领域结果、路由和计数器保持独立。

不把 `status`、`route`、`stop_reason` 合为一个字段：它们分别表示业务事实、下一步路由和终止原因。工单、质检、审批及产线状态也不共用一个枚举。

`step_history` 与 `completed_steps/failed_steps` 在顶层 Runtime 中记录的粒度和形状不同。本轮保留已有可见字段，先集中记录逻辑，不能因为名称相近就直接删除。`runtime_outputs` 与领域结果字段保留当前响应契约，不通过删字段造成前端或审批恢复丢失上下文。

移除仅有声明、无读取/写入、无响应契约依赖的字段。删除旧编排后再复核其专属字段；有持久化或历史快照消费者的字段继续在兼容读取边界接受，不改写旧记录。

## 6. Tool 的实现与权限边界

库存薄封装共用事实查询；`stock` 投影、`available` 计算和 `part_no` 优先级仍按原工具契约处理。尤其不能把未知库存当作有库存，也不能将本地演示库存提升为真实数据。

RAG 查询共用检索执行函数，但报警、SOP、手册、案例和语义记忆仍各自施加原过滤条件。手册检索对 alarm_code 的处理不能被通用合并改变。

CAD 查询共用结构化条件和结果整理，但设备范围、部件/零件号精确匹配、名称模糊匹配、关系与位置结果仍保留。指定设备不能退化为全库查询。

ToolRegistry 统一维护名称、处理器、描述和所属外部服务的元数据，减少平行字典漂移。已有名称仍可调用；工具权限必须先按请求中的实际名称检查，再进入共用实现，不能通过别名绕过白名单。

对只有定义、没有直接源码调用的工具继续检查 Skill、动态 Action、HTTP 工具接口与兼容导出。无法证明没有消费者的工具不删除公共入口；仅消除内部重复实现。

所有副作用动作继续分开进行审批、幂等和对账。超时不转为成功，也不因合并增加写操作重试。

## 7. Markdown Skill 整理

只合并触发规则、权限范围相同的重复定义。CAD 的图纸/部件查询整理为一个主定义；Router 的默认实体提取与意图路由整理为一个主定义。旧名称通过显式别名解析，不再复制同一份实现。

注册表对主名称、别名冲突和工具引用进行校验。显式选择旧名称必须能找到对应主定义；同一主定义被多个别名选中时只激活一次。日志记录规范 Skill 名称，并在旧名称输入时记录实际请求名称，避免历史记录无法对应。

同名或别名解析不能扩大工具权限。Quality 的尺寸专项与综合检测工具范围不同，继续保留各自定义；Diagnosis 的严重故障安全分诊也保留。

Skill 正文与 Front Matter 的步骤对应真实节点或真实子操作。不保留仅为增加流程长度而列出的虚构执行步骤。知识、Memory 与报告中语义不同的触发分支保留，不强行压成一个“大 Skill”。

## 8. 错误处理与既有未完成项

配置缺失、服务不可用、空证据和数据不完整继续返回明确的失败或证据不足，不能以默认值制造成功。日志保留调用输入、输出、错误、任务归属与上下文，同时不暴露密码、会话令牌和供应商密钥。

上一轮虚拟产线功能仍存在需要单独收尾的项：迟到复机结果的 generation/attempt 隔离、提交成功但响应丢失后的对账、部分后验成功后回停的工单关闭门禁、并发派工负责人覆盖、停机读回失败后的人工恢复路径。这些不是本轮精简完成的证据，也不作为可以删除安全存储或状态的理由。本轮不扩展修改产线控制业务；其相关文件和未提交内容保留，回归出现相关失败时如实记录。

## 9. 验证与交付

每组变更先补特征或回归测试，再修改实现。原本正确的重构以修改前后等价特征测试证明；实际问题则先确认新测试能复现问题。不得删除失败测试、降低门禁或扩大跳过范围。

必须覆盖：

- 九个 Agent 的有效请求、无效请求及准备阶段阻断。
- Quality 五项检测保留，缺失数据不能合格。
- 工具新旧入口参数、结果、外部调用次数与权限拒绝一致。
- Markdown Skill 主名称/别名、重复选择、冲突、工具范围和日志身份。
- 正式 Runtime 的低置信度、维修必要性、证据、审批、幂等和经验学习门禁。
- task_id/trace_id 归属、真实输入输出、失败步骤，以及审批恢复上下文。

使用隔离配置、临时存储和测试外部适配器，不调用生产数据库、收费模型或真实设备。各服务同名 app 包继续独立测试进程运行。依次执行针对性回归、Agent 服务测试、必要的跨服务契约；其他服务只在其代码或共享契约实际受影响时执行对应回归。

不设置“必须删除多少文件”的指标。交付报告列出实际减少的图节点、重复实现与 Skill 文档，保留项及原因，测试命令与通过/失败/跳过数，以及未执行验证。离线测试通过不等于设备或生产验收通过。

## 10. 备份与恢复

实现前将每个将修改或删除的源码、Skill 与测试按仓库相对路径备份到 `.runtime/backups/agent-runtime-slimming-20261003/`，保存当前已修改版本，不从旧提交覆盖。记录文件清单与校验摘要，不复制密钥、生产配置或业务数据库。

恢复时先另存当前文件，再按清单逐个恢复；不整目录覆盖，不使用 git reset/checkout 回退已有工作。新增文件单独列出，只在确认无新增内容后处理。本设计为新增文件，本轮尚未修改或删除产品源码。

## 11. 设计自检与阶段

- 范围限于已存在的 Agent 编排、状态、工具与 Skill，未引入新业务系统。
- 不改变九个 Agent 的职责、五服务边界或现有安全门禁。
- 不以低调用量、没有直接字符串调用或测试导入为理由盲目删除。
- 兼容名称、结果投影、权限及历史状态均有明确处理边界。
- 保留已有未提交修改，不将上一轮未完成的产线功能宣称完成。
