# Industry-Agent：Skill Loop 自进化飞轮更新方案

日期：2026-10-12。依据用户提供的“Skill 自进化飞轮”图和当前本地代码核对。

状态：更新后的设计方案，尚未实施本文新增模块。已有的自动稿、人工审核/测试/发布仍按 `docs/skill-evolution.md` 运行。不得把本方案能力列表当作已完成代码清单。

用户确认：本方案是 **Skill Loop（技能优化循环）**，不是 Agent Loop（业务任务执行循环）。两者不得在代码命名、状态、日志或专家中心展示中混用。

## 1. 更新目标和边界

目标不再是“遇到一条失败日志就给 Skill 追加说明”，而是：知道哪个技能在什么版本、什么场景下退化，选择值得优化的对象，提出小幅改动，用独立的测试核对，再由人工发布，最后记录效果是否真的改善。

核心链路：

```text
真实运行与版本归因
  → 周窗口健康统计
  → 有证据的候选排序与预算
  → 最小修改稿 + 修改说明 + 测试预期
  → 人工审核 → 同基线对照 → 模拟闭环测试
  → 人工发布
  → 新版本观察与审计回流
```

保留原图 L0–L5 六层，但它们是后台逻辑分层，不是新增六个 Agent、六个 Graph 节点或六套工具。复用现有 Agent 服务、Model 服务、轨迹、Skill 注册表、测试和专家中心。业务诊断循环与 Skill 优化循环必须分开：前者处理当前故障，后者维护规则，不能因为等待周级优化而延迟故障诊断。

### 1.1 Skill Loop 与 Agent Loop 的明确关系

| 边界 | Skill Loop：技能优化循环 | Agent Loop：业务执行循环 |
| --- | --- | --- |
| 优化/执行对象 | 一个明确版本的 Skill 规则与说明 | 当前故障、知识问答、CAD 等具体业务任务 |
| 输入 | 已完成运行的受信日志、版本归属、校验结果 | 当前任务输入、业务上下文与工具观察 |
| 循环动作 | 观测 → 分析 → 候选 → 修改稿 → 人工审核与测试 → 人工发布 → 效果观察 | 按现有业务图执行规划、工具调用、观察、校验及后续动作 |
| 输出 | 待审核修改稿、测试回执、人工发布的新版本及效果记录 | 业务结果、工单、图纸或其它任务产出 |
| 状态归属 | 独立的优化周期与候选状态 | 原业务任务、执行尝试及工单状态 |

两者通过两条有边界的数据链关联，而不是合并成一个执行循环：

```text
Agent Loop 的真实运行日志 → Skill Loop 的只读观测输入
Skill Loop 经人工发布的版本 → 后续业务执行按现有加载规则使用
```

Skill Loop 不插入业务图、不改变业务循环次数，也不能用优化状态覆盖任务或工单状态。不会因某个优化稿仍待审核或测试而暂停正常业务。修改稿不直接进入线上任务，发布不改写已经记录的版本归属，也不额外强制进行中任务热切换。

测试阶段可以调用已有隔离验证机制，其中可能执行一次原业务 Agent Loop；这是验证候选技能的测试运行，不代表两个 Loop 合并。测试必须标记试验来源，禁止将自身试验记录重新作为生产不足触发下一份优化稿。

命名和展示继续使用现有 `skill_evolution` 入口及命名空间；新增周期明确标为 `skill_loop`，保留独立周期编号和原业务运行关联，不将其命名为业务 `agent_loop`。专家中心显示“技能优化循环”，业务日志仍显示实际 Agent 执行；本节是实施约束，不宣称新增周期记录已上线。

继续遵守用户此前确定的约束：系统自动准备稿件、修改说明与预期；人工审核、点击测试并最终点击发布。没有自动生产发布、真实设备控制或自动回退。监督身份仍以查看和催办为主，新增操作沿用真实维修身份、同源及服务端审批规则。

## 2. 与原图相比需要调整的内容

| 原图内容 | 本项目采用的调整 | 原因 |
| --- | --- | --- |
| 周级大循环、亚周级微循环 | 每分钟收集与告警；每周形成候选计划；人工触发后及时推进测试 | 收集不能一周才做一次，优化也不能对每条日志重复收费 |
| 每周 Top-K，预算补足至 K=3 | 首期最多 3 个有足够证据的技能，不足 3 个不强行补齐 | 不用健康、未使用或未知技能凑满模型调用次数 |
| 置信度加权 verdict | 原始 verdict 独立记录；模型置信度只作辅助特征 | 模型自报高置信度不能证明答案正确 |
| PSI、MMD、KL 漂移检测 | 先做同群体的窗口趋势；满足样本和基线条件后再增加统计漂移 | 当前没有可靠的全量分布基线，不先堆算法名称 |
| embedding 失败聚类 | 先按错误码、校验项、场景和工具阶段归并；有规模后经 Model 服务增加向量聚类 | 避免引入新的直接供应商调用和无必要的向量成本 |
| Pareto + Thompson bandit 排序 | 先采用可解释的非支配分层与确定性排序；有可比收益后再考虑 bandit | 当前没有真实 `last_gain` 奖励，不能初始化成伪收益 |
| 多智能体根因分析 | 首期复用现有模型生成器，一次有界分析返回假设、依据及最小规则 | 根因必须有证据，不新增重复 Agent 调用 |
| 自动影子 → 小流量 → 全量 | 只读对照评测 → 虚拟工厂闭环 → 人工发布 | 项目只有一条产线，当前没有按版本隔离的生产灰度路由 |
| git 棘轮、自动 revert | 版本快照、发布审计；人工选择旧版生成恢复稿，再测试发布 | 本地项目不强制依赖 Git；恢复也不能绕过最新验收门禁 |
| HITL 人工抽检 | 每次修改都人工审核、测试并最终发布 | 用户最新明确要求，不能退回抽检或自动上线 |
| results.tsv 作为回流 | MySQL 保存结构化数据，按需导出 TSV | 表格是导出物，不新增并行的长期数据库 |

## 4. L0：数据观测层

### 4.1 最小可信运行记录

以服务器生成的 `agent_run_id` 关联 Agent 终态、Skill 步骤和工具调用，另保留 `trace_id`、任务、业务事件及稳定记录编号。一次事件中的多 Agent、多尝试不能混成同一次调用；重复记录按稳定身份去重。

至少记录：

- Agent 名称、真实 Skill 名称、实际使用版本和内容指纹。
- 步骤、工具名称、阶段、输入输出摘要及耗时；原始正文通过已有审计权限读取，不复制密钥或全部上下文。
- 场景、数据/工具适配器来源、模型标识（实际可取得时）、validator 版本。
- 业务校验结果及依据、降级、基础设施错误、缺失字段和截断标记。
- 是线上任务、只读回放还是专家机器测试；专家测试不得再变成优化触发来源。

版本指纹在选择/执行技能时取得，不在任务结束后重新读取文件冒充当时版本。同一任务使用了混合版本，应明确标记，排除新旧收益对照。旧日志没有版本时保留未知，不按当前版本补值。

### 4.2 verdict 和统计口径

| 分类 | 依据 |
| --- | --- |
| pass | 当前执行/证据校验实际通过；只表示该校验范围内通过，不表示所有技术结论正确 |
| fail | 明确业务 validator 失败或可归因的业务执行失败 |
| degraded | 明确 fallback、证据不足、检索降级等 |
| unknown | 缺少终态、技能归属或必要判定依据 |
| infrastructure_error | 连接、超时、余额、模型不可用等；独立统计，不归因于 Skill 规则质量 |

不要把工单存在、HTTP 200、`completed` 文本或模型自报置信度单独当作 pass。未知项不从分母悄悄删除；分别展示已知判定的比例与数据完整率。

### 4.3 时间窗口与存储

建议以 Asia/Shanghai 周一 00:00 划分周窗口，数据库保留 UTC 原始时间。外环使用上一个完整周；当前周仅作早期趋势。首次无完整周数据时进入冷启动，展示可用样本，不声称拥有基线。

扩展现有 MySQL 轨迹查询：按明确窗口、固定最大 sequence_id 和游标分页，使用有界投影，不重复扫描全部大 payload。聚合结束记录来源范围、数量、缺失和完整性；未读完不能伪装完整周。

长期窗口快照、周计划、预算、评测和发布效果复用 MySQL JSON 存储。Redis 可存临时进度/缓存，不作为发布、预算或历史的唯一真相。不引入 SQLite 或 TSV 文件数据库；迁移保留旧数据。

## 5. L1：健康诊断层

每个 Skill、每个实际版本建立四项健康画像：

1. **业务失败/降级**：调用量、verdict 分布、失败项分布、失败 EWMA。
2. **执行覆盖**：实际执行声明步骤及适用场景的覆盖；步骤覆盖不等于所有业务场景覆盖。
3. **陈旧程度**：最后实际执行、最后人工验证、最后发布时间分别展示。长期未使用不是“已退化”。
4. **上次收益**：仅使用合格的同基线新旧对照；没有对照则 `not_evaluated`，不填 0 或正数。

成功基线按同类场景、数据适配器和模型条件分组，不能把换供应商、数据服务故障或工作负载变化说成 Skill 退化。仅在完整窗口、可比群体和样本量满足批准的统计策略时提示趋势/漂移；否则提示“样本不足”。统计阈值不是工业设备合格阈值，两者不能混用。

首期先支持失败趋势、耗时及工具组合的可解释变化；PSI/MMD/KL 作为后续扩展，不默认全部启用。没有真实失效标签时，漂移召回率显示未评估。

## 6. L2：进化决策层

### 6.1 候选资格

- 有可关联的真实业务不足，不是纯基础设施故障或专家自身测试。
- 修改的正文确实被相应执行路径使用，或本次明确为说明维护，二者不能混淆。
- 当前版本和适用场景可核对，未有同技能未结束的修改稿。
- 有可执行的测试方式和待验证预期；缺少必要证据则先补充来源，不生成确定性根因。

项目中的诊断正文会进入模型消息；CAD 复杂需求解析会使用建模 Skill 正文；知识检索和 CAD 工程查询还存在代码中的固定循环逻辑。不能声称编辑正文就能修改这些固定算法，不能让 instruction_preview 获得完整发布资格。

### 6.2 排序与预算

先按多目标非支配关系分层，再用确定性、可审计的规则排序。展示失败量/比例、降级、覆盖缺口、样本量、最近优化时间和去重簇，不让任意一项模型 confidence 决定优先级。同分使用稳定标识排序，确保重复计算一致。

建议首期每周最多选择 3 个满足资格的 Skill；不强制补足 3 个。候选计划记录当时的数据快照和排序理由，更新计划必须留新修订，不能事后改写当周选择的依据。

周预算通过 MySQL CAS 跨进程预留，进程重启不重置。模型生成失败和超时同样消耗已发起的额度，不通过反复重试绕过预算。默认串行执行，实际金额/usage 不可取得时标记未知，不能把请求次数上限说成精确费用封顶。

首期不用 Thompson sampling。以后只有取得多轮可比收益、明确奖励定义和费用数据，才讨论 bandit；不能用“成功创建稿件”作为奖励。

## 7. L3：进化执行层

沿用现有生成器，不另建一套自动写 Skill 的入口：

1. 根据候选的失败记录定位实际步骤/工具阶段。
2. 按校验项、场景和工具阶段归并重复失败，输出来源编号及聚类依据。
3. 把“已观察事实、可能原因、尚缺证据”分开；模型提出的是待核对假设。
4. 对一个当前版本提出一个最小变更目标，追加少量业务规则，避免全局重写。
5. 输出原基线、差异、来源、修改说明、预期结果和测试建议；存入候选而非线上文件。

修改说明自动回答“为什么选中、哪里不足、准备改什么”；预期自动回答“测试时应观察到什么变化”。没有新规则实际生效路径时明确说明维护范围，不借优化名义改变图调度、工具白名单、审批、硬预算或设备阈值。

模型及日志是分析数据，不能自报人工批准、测试通过或授权真实设备操作。保留当前 sensitive-content 检查、字段限制、哈希绑定和一次有界模型调用。参数或基线变化需重新审核和测试。

## 8. L4：验证守门层

### 8.1 三个独立门禁

```text
静态契约/安全检查
  → 同基线只读对照
  → 项目适用的完整虚拟业务测试
  → 人工核对实际结果
  → 人工发布
```

同基线对照不是重复调用生产接口。保存冻结的输入、受信工具观察、模型/测试适配器条件和 validator 版本；旧版与候选在同一基线中执行。回放只接只读适配器，禁止派工、数据库写入、停机、复机、学习写入和重新发送历史命令。

样本集划分用于生成的分析集和独立 holdout；样本哈希、来源版本和划分方式留痕。不得把模型已用于写稿的样本又当作唯一独立验证集，不因候选失败删掉样本。

### 8.2 收益判定

分别报告校验通过差异、安全/证据回归、耗时、调用和费用差异。模型自然语言评分不能替代现有 validator 或可信业务事实。

只有样本完整、基线可比、相关路径真实执行，并有批准的非回归/收益标准时，才计算 `last_gain` 和保留/拒绝结论。收益阈值、最小样本及统计置信策略须由项目验收策略定义；未定义、样本不足或不支持真实回放时显示“未评估”，不是“提升 0%”或“已优化成功”。

当前 `MachineTrials` 完整闭环门禁继续保留。只读对照、诊断样例或 instruction_preview 都不能替代 `machine_flow` 完成、所选技能实际执行、当前依赖未变及原时效检查。对于无法被设备故障链覆盖的知识问答/CAD 场景，需要先补对应的真实、无生产副作用验收；不伪造故障来制造通过。

### 8.3 发布和恢复

测试通过停在 `awaiting_publication`，必须人工最终点击。复用 SkillManager 原备份、原子替换及 MySQL 发布栅栏；文件/数据库提交不确定仍只读对账。

暂不实现生产自动灰度，也不直接自动恢复旧文件。恢复时选择旧版本快照，生成一份以当前权限和基线为准的恢复稿，再审核、测试、人工发布；保留旧/新哈希、恢复原因与关联审计。历史只追加，不删除失败或被拒绝版本，不依赖自动 Git 命令。

## 9. L5：状态与治理层

外环计划建议使用：`collecting → profiled → planned → drafting → awaiting_review → validating → awaiting_publication → published → observing → assessed`。这是优化周期状态，不能冒充业务工单状态；候选仍复用现有 confirmed/verifying/published 等实际状态。

治理要提供：

- 候选、预算预留、测试启动和发布分别幂等，写回执不确定时不重放。
- 暂停新建议、费用/次数/并发上限及超时；“暂停优化”不能被误解为停止机器。
- 每次修改的来源、diff、人工身份、测试、发布、观察及恢复关联。
- 过期、无效会话、基线变化、测试失败退出活动槽，不永久挡住下一周期。
- 后续运行按真实版本归因；跨版本或跨模型不可比结果不计为新版本收益。
- TSV/报表只导出结构化历史，敏感信息不进入导出或模型上下文。

北极星指标区分两类：有严格对照的质量收益，与纯运营指标（计划、人工审核、测试门禁、发布和恢复数量）。漂移召回率需要真值；门禁通过率需要完整测试记录；回滚率只是恢复比例，不代表业务恢复成功。

## 10. 专家中心页面更新

保持纵向布局，继续使用现有技能名称、作用、正文、修改说明及预期字段，不再增加一套编辑器。

上方新增“技能运行健康”：本周/上周有效样本、业务失败/降级/未知、步骤覆盖、最近运行、最近验证、收益是否评估及统计完整性。

中间新增“本周优化计划”：最多 3 个有资格候选，显示选中原因、来源问题、排序依据、剩余额度和正在等待的人工动作。没有有效候选明确为空，不填演示数据。

下方沿用当前编辑区：自动填写正文、修改说明与预期，人工审核并测试。新旧对照以“旧版结果、新版结果、可观察差异、缺失证据”上下展示。测试通过后由人发布。历史版本与恢复稿入口不执行直接覆盖。

## 11. 最小模块边界和实施次序

建议保持 `SkillEvolution` 为唯一协调入口：

| 顺序 | 落地范围 | 主要位置 |
| --- | --- | --- |
| A：可信观测 | 实际 Skill 版本归因、周窗口分页、verdict/完整性、MySQL 健康快照 | 现有 `agents/base.py`、`harness`；小型 evolution analytics 模块 |
| B：有界决策 | 可解释排序、周 Top-K、跨进程预算与暂停 | 现有 `evolution.py`/worker/store；小型 planner 模块 |
| C：最小执行 | 同源失败归并、增强修改说明/预期/差异 | 复用生成器与 expert API，不新增生产工具 |
| D：可验证收益 | 支持路径的冻结样本只读 A/B、holdout及非回归门禁 | 独立 replay 模块、原 trials；先诊断，再按真实能力扩展 |
| E：治理回流 | 真实版本观察、评测记录、专家历史与恢复稿、前端健康/计划 | 复用 MySQL、原发布审计和专家中心 |

不是先建 6 层空壳、生成固定健康数据再补业务。每阶段先有真实函数/API回归；没有可靠数据或执行适配器则明确标记不可评估。

现有五服务架构、模型供应商、CAD MCP 路径、正常派工、设备控制/维修确认和质检规则均不因本方案改变。测试使用隔离数据库、模型与设备传输适配器；不启动生产部署，不调用真实设备，也不自动进行收费模型回放。

## 12. 验收用例与未完成项

后续实施至少验证：

1. 多 Agent、多 Skill、多尝试和重复轨迹不会错误计数；缺少归属标 unknown。
2. 发布期间任务使用旧版本或混合版本时，不错误归因于新版。
3. 不完整周窗口、查询失败、旧日志缺版本时不显示虚假完整统计。
4. 基础设施错误不触发规则质量优化；专家与自身回放不重复触发。
5. Top-K 不强行凑数；并发进程、超时和重启不超周预算。
6. 候选保留原执行元数据，模型/客户端不能给自己审批。
7. 旧版/候选实际执行相同冻结输入与观察；回放无业务写入；holdout不泄漏到生成。
8. 无真实收益时显示未评估，差异与阈值不足不能冒充通过。
9. 新评测不能降级原发布门禁；过期、会话撤销、依赖变化仍禁止发布。
10. 人工恢复追加新版本和审计，不删除历史、不盲目重试文件写入。
11. 前端刷新、切换身份、迟到响应和已编辑草稿保护继续有效。
