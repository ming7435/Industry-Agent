# Industry-Agent 工业智能运维平台项目说明书

## 1 项目背景

工业设备运维涉及运行数据、报警记录、维修手册、工程图纸、备件信息和历史案例。故障处置需要将这些信息与具体设备、异常现象和作业任务关联，形成维修方案，并确认处理后的设备状态。

在传统流程中，设备监测、资料查询、维修派工和结果记录分别完成，信息传递依赖人工整理，容易造成分析依据分散、任务衔接不连续和处理结果难以追溯。生产质量管理还需要贯通检测、整改、复检和放行，保持零件质量与设备运行记录的关联。

Industry-Agent 结合多智能体协作、检索增强生成和业务规则，将设备异常分析、知识与工程资料查询、维修执行管理及生产质检整合到统一工作台，建立从数据采集到结果确认、从业务记录到经验积累的连续处理流程。

## 2 项目定位与建设目标

项目定位为工业设备运维与生产质量协同平台。系统以设备数据为输入，以维修知识和工程资料为依据，通过专业 Agent 协作提供分析建议与处理方案，由业务服务管理任务执行、状态变化和结果确认。

建设重点是统一设备、异常、人员、工单和质量信息的访问入口，增强故障分析与资料检索能力，贯通维修派工、人员反馈和设备恢复验证。通过报告生成与经验提取，系统将有效处理结果沉淀为可查询、可复用的业务知识。

## 3 总体架构

### 3.1 架构概述

系统按展示层、接入与网关层、业务服务层、Agent 智能核心层、能力执行层、外部系统与数据层、基础设施层七个逻辑层次组织职责。五个业务服务分别承担智能编排、业务管理、知识检索、模型调用和工程资料查询，Monitor 独立提供设备采集与工作台入口，FreeCAD 提供本机工程计算能力。

展示层呈现设备监控、诊断、维修、质检、知识、CAD、报告及执行轨迹。接入与网关层负责统一访问、请求转发和身份校验。Agent 智能核心组织任务规划与专业协作，能力执行层通过技能、工具和适配协议连接业务服务及工程内核。外部系统与数据提供运行信息、专业资料和持久化资源，基础设施支撑部署、验证与运行观测。

### 3.3 服务组织

Monitor 采集设备状态并执行异常规则，将确认的事件提交给 Agent 服务，同时提供工作台资源和同源 API 转发。Agent 服务负责任务规划、专业 Agent 协作、工具调用和结果校验；Backend 服务管理账号、工单、库存、质检、报告及经验，维护业务状态和持久化记录。

RAG 服务处理知识资料，提供关键词与向量检索、融合、重排和引用组织。Model 服务集中适配外部模型，向其他服务提供对话、向量化、重排和视觉接口。Document-CAD 服务查询图纸、BOM、部件、装配关系和安装位置；本机 FreeCAD 承担实体建模、工程图计算和文件导出。

### 3.4 数据组织

账号、工单、质检、报告、经验和持久化执行记录由 MySQL 保存。Redis 管理登录会话、阶段进度和临时建模状态，Milvus 与 Whoosh 分别维护向量和关键词索引。原始文档、图纸、报告及模型文件保存在对象存储或本地文件目录。

设备、异常事件、维修方案、工单和处理结果通过业务标识关联。知识索引服务于检索，业务处理结果以持久化记录、有效检测证据和设备实际状态为依据。

生产仿真另行保存不可变生产方案、加工产出和参数检测记录，完整关联 CAD 版本、生产人员、批次、执行程序及工厂任务。程序与回执以原始 JSON 文本保存，避免业务库的数值序列化改变摘要；模拟结果与正式生产零件、质量放行记录分别存储。

## 4 技术栈与关键设计

### 4.1 前端与服务开发

前端采用 React 组织业务页面，使用 Vite 完成构建，Three.js 提供三维模型预览、视角操作和运动数据展示。后端采用 Python、FastAPI 和 Uvicorn 提供 HTTP 服务，Pydantic 负责请求结构与参数校验。前端统一呈现信息，服务端维护业务状态及执行规则。

### 4.2 智能体编排与能力执行

智能编排采用 LangGraph 与自研 Runtime。LangGraph 承载顶层执行状态，Runtime 管理输入解析、任务规划、动作表达、策略审批、能力分发和结果评估，并通过有界循环与执行管理控制任务推进。

系统配置路由、诊断、知识、CAD、维修、工单、质量、报告和记忆九类 Agent，在 Agent 服务内按专业职责协作。能力注册中心维护能力与 Agent、工具及策略的关联；Markdown Skills 声明领域步骤和工具范围，Tool Registry 校验工具输入及调用范围，MCP 适配连接专业服务和本机工程内核。A2A 管理进程内结构化协作请求，Trace 关联任务、Agent、工具调用与结果。

### 4.3 模型与知识检索

模型调用统一经过 Model 服务，对接 DeepSeek、SiliconFlow 等提供方，支持分析生成、向量化、重排和视觉处理。模型输出形成候选分析与建议，具体业务操作继续执行服务端规则校验。

知识检索采用 Whoosh/BM25 关键词检索与 Milvus 向量检索，结合 BGE-M3 向量化、RRF 融合和 BGE 重排模型筛选相关资料。关键词检索匹配设备名称、报警码和专业术语，向量检索补充语义相关内容。结果保留资料来源，为诊断、知识回答和维修方案提供依据。

### 4.4 工程计算

工程计算采用 FreeCAD 与 MCP。系统根据明确规格生成受约束的建模请求，调用本机工程内核完成实体生成和几何校验，提供三维预览及 STEP、STL、FCStd 导出，并扩展支持限定范围的装配、运动展示和工程图能力。

已有工程资料由 Document-CAD 查询，新建模型由 CAD Agent 调用 FreeCAD 生成。工程产物与对应运行记录关联，保留从输入规格到导出文件的处理依据。

有效建模版本可经 CAD Agent 转换为受限虚拟车削程序，通过回环接口交付当前模拟工厂的 TRAK TC820 执行器。程序提交与加工启动分别授权，执行器按确定刀路运行并返回加工区尺寸、进度和事件记录；Runtime 在页面关闭后仍持续核对并保存执行事实。

### 4.5 存储、部署与运行控制

存储采用 MySQL、Redis、Milvus、Whoosh 及 MinIO/S3 或本地文件目录，分别管理业务事实、临时状态、知识索引和文件资源。Docker Compose 组织服务部署，Nginx 提供访问入口，GitHub Actions 执行服务契约验证与容器构建。执行轨迹与结构化日志支持过程回溯，并可配置 OpenTelemetry 输出观测数据。

业务操作通过人员身份、任务归属、状态规则和幂等机制控制。诊断与方案保留证据依据，维修恢复结合人员反馈及启停前后数据确认，质量放行依据有效检测与复检记录判定。

## 5 核心业务流程

### 5.1 设备运维

Monitor 采集设备状态并识别异常，诊断 Agent 分析报警与运行数据，知识和 CAD Agent 提供资料依据，维修 Agent 组织处理方案，工单 Agent 调用 Backend 完成任务创建和派发。

维修人员按任务执行作业并提交实际反馈。系统结合关联故障和设备状态进行恢复验证，将确认结果用于报告生成与维修经验沉淀，形成“设备采集—异常识别—智能诊断—维修方案—工单派发—人员维修—恢复验证—经验积累”的闭环。

### 5.2 生产质量

质量流程以生产零件身份、设计规格和实测数据为基础，组织尺寸、外观、材料、功能和工艺五类检测。异常结果进入申诉或整改流程，整改完成后以有效复检记录判定结果，通过后放行并关闭。

生产质检与设备维修分别管理处理状态，通过设备、零件和业务记录保持关联。

### 5.3 工程辅助与业务总结

维修场景通过工程查询定位图纸、BOM、部件关系和安装位置；生产建模场景通过 FreeCAD 生成模型及工程文件，由工作台提供预览和下载。报告与记忆能力汇总既有业务记录，将经确认的处理结果形成报告和可复用经验。

### 5.4 生产仿真与参数检测

生产建模、工厂执行和产出检测形成独立流程。CAD Agent 负责锁定通过实体及 STEP 回读校验的完整设计版本，生成、保存并下发虚拟加工方案，按人员明确操作启动加工；Runtime 负责身份校验、Agent 调度、持续对账及恢复后的事实补齐；Quality Agent 将已保存产出的加工区外径、有效长度及通孔直径与原始设计精确比较，保存一致、不一致、缺测或待复核结果。每项检测保留设计值、工厂模拟值和偏差，批次统计按设计版本、来源及生产人员隔离。

当前支持毫米制实心圆柱和单个同轴贯通孔，执行范围限定为加工区仿真。暂停或中断任务须经人员明确操作继续；未知提交按原指令核对，避免重复执行。质量页面区分“工厂产出检测”与“比对仪数值演示”，日志按“生产准备—模拟加工—模拟检测”呈现后台保存的阶段事实。该流程不包含真实机床控制、完整 CAM、切断取件或实物计量，模拟尺寸一致性不构成制造公差验收及正式质量放行依据。

## 6 项目价值与应用范围

项目将运行数据、专业知识和业务执行连接到统一工作台，使故障分析具有资料依据、维修任务具有连续记录、处理结果具有验证过程。多智能体提供专业分工，知识检索支持资料获取，业务服务维护处理状态，报告与经验机制支持长期积累。

当前设备接入与控制基于模拟工厂，系统用于业务联调和场景演示。服务和适配层为后续接入实际设备与业务系统提供实现基础。
