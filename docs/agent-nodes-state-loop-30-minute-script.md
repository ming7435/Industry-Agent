## 第一节：开场：先把三个概念分清楚〔00:00–02:00〕

大家好，今天我只讲这个项目里最核心的三个概念：Agent 的节点、状态，以及 Agent Loop，也就是智能体循环。我不会把所有页面和服务都重新介绍一遍，而是回答一个更具体的问题：一个故障进来以后，系统究竟怎样一步一步取得信息，形成判断，并且决定继续还是停止。

为了方便理解，我们可以先把一个 Agent 想象成一名有明确职责的工作人员。节点，是这名工作人员当前正在做的一个处理阶段。状态，是他手上不断更新的任务资料。循环，则是他看完新的资料以后，发现还不能下结论，于是再去查一次，再判断一次。

这三个概念并不是三种不同的模型。节点可能只做数据转换，状态本质上是结构化数据，循环也可以由确定性的代码控制。只有某些需要理解、推理或者生成内容的操作，才会调用模型。因此，不能看到一个节点，就认为这里一定调用了一次大模型。

今天的讲解以当前本地代码为依据。现在设备侧使用的是虚拟工厂，所以后面提到的故障例子，是为了说明程序如何处理数据，不是宣称真实设备已经完成故障定位，更不是宣称系统能替代真实产线的安全控制。

我希望大家听完以后，能够把三个问题讲清楚：第一，为什么节点数量不等于工具调用数量；第二，为什么程序执行成功，不等于维修完成；第三，为什么 Agent 有循环，但不能一直循环，也不能为了得到一个答案而重复执行有副作用的动作。

接下来，我先介绍当前的 Agent 分工，再讲节点和状态，最后用诊断、知识检索和工程定位三个例子，把循环完整串起来。

## 第二节：九个 Agent 与节点统计口径〔02:00–05:00〕

当前项目里有九类 Agent。它们分别负责路由、诊断、知识检索、工程定位、维修方案、工单、质量检测、报告和经验记忆。这里的九个，是九种领域执行者，不是九个模型供应商，也不是九条生产线。

路由 Agent 负责理解用户要做什么，并提取设备、报警、工单等业务实体。它有三个节点，分别对应准备、请求路由和结果结束。路由只是确定任务方向，不意味着系统已经批准某项业务操作，更不能因为用户说“已经审批”，就直接授予写入权限。

诊断 Agent 负责结合报警、快照、历史与日志，判断可能的故障原因。它有七个节点。知识 Agent 负责寻找文档、标准作业规程和案例等证据，有六个节点。CAD Agent 负责工程定位，查询零件、图纸、物料清单和部件关系，有五个节点。这三类 Agent 的领域图都存在明确的循环路径。

维修方案 Agent 有六个节点，负责把诊断和资料组织成方案。工单 Agent 有七个节点，负责创建、派工，以及已有工单的查询和执行动作。维修方案回答的是“怎么修”，工单回答的是“谁来修、修到哪一步、反馈是什么”。它们相关，但不能混为一份结果。

质量 Agent 有五个节点，检测对象是生产零件。报告 Agent 也有五个节点，汇总已有业务记录。记忆 Agent 有七个节点，负责经验检索或符合条件的经验保存。记忆不是自动更新模型权重，而是管理可以再次检索使用的案例与知识。

把九个领域图中的实际节点相加，得到五十一个。这是当前已编译领域图的统计，不是从文档里数步骤，也不是从前端流程图里数方框。一个节点可以被多次执行，所以五十一个节点并不表示一次任务固定执行五十一次。

此外，顶层编排图另有一个运行时节点。如果连这个节点一起统计，就是五十二个显式节点。但我下面说“五十一个”，始终只指九个领域图，不包含框架的开始和结束标记，也不包含运行时内部的普通函数。

这两个统计口径必须说明白。否则，我们可能把一个函数、一个技能步骤、一条日志和一个真正的图节点全部加在一起，得到一个很大的数字，再误以为系统过度复杂。判断架构是否合理，首先要确定自己到底在数什么。

## 第三节：节点是什么：阶段、子操作与图的边〔05:00–08:00〕

现在来看节点。项目里的领域流程主要用 LangGraph 的状态图表达。通俗地说，图里有处理阶段，也有阶段之间的连接。一个节点接收当前状态，执行自己的操作，再返回需要更新的数据；图根据连接和条件，决定下一步去哪里。

普通连接表示顺序执行。例如，维修方案在收集上下文以后进入方案构建。条件连接则表示分支。例如，诊断节点拿到模型响应以后，如果里面有工具请求，就去工具检查；如果已经给出候选结论，就去结果校验。分支依据是状态里的实际结果，不是前端动画播放到了哪个位置。

当前代码做过节点合并，合并的是调度层的阶段，不是简单删掉业务步骤。以准备节点为例，它内部仍然先初始化请求，再加载技能。初始化负责整理输入和建立上下文，技能加载负责选择当前任务允许使用的能力。两件事仍然发生，只是不再为了它们分别增加一次图调度。

另一个例子是诊断里的“执行并观察”节点。这个节点先调用通过检查的工具，再把工具返回转换为观察和证据。如果工具调用结束了，却没有把返回写入状态，下一次模型就仍然不知道工具查到了什么。因此，执行和观察可以安排在同一阶段，但不能漏掉观察这个真实操作。

代码中还有一个顺序组合器，负责让多个子操作依次执行。它会把前一个操作的更新带给后一个操作。如果遇到明确的停止路由，就提前结束这个组合。异常也不会因为被组合进一个节点，就自动重试。合并节点的目标，是减少空跳转，而不是掩盖失败。

结束节点同样是一个统一入口。正常路径可以构造正式结果，回退路径可以构造不足或降级结果。共用一个结束节点，不等于两种结果一样。真正决定含义的，是输出中的业务状态、校验信息和停止原因。

这些子操作仍然有自己的执行轨迹。也就是说，调度图可以更简洁，但日志仍能看到初始化、技能选择、工具调用和结果校验分别发生过。这里需要区分“图里的节点数量”和“日志里的操作数量”：后者多于前者，并不一定说明存在重复任务。

所以，判断一个节点是否有价值，不是看它名称是否高级，而是看它是否承担独立的决策、验证、分支或者副作用边界。必须独立判断的部分应该保留；总是顺序执行、没有必要单独跳转的部分，可以组合起来。这样既减少调度复杂度，也保留真正重要的业务检查。

## 第四节：状态是什么：任务资料如何在节点之间传递〔08:00–11:00〕

接下来讲状态。这里的状态，不只是页面上“处理中”三个字。对于执行图来说，状态是一份随任务一起流动的结构化资料，里面既有输入，也有中间结果、证据、轨迹和下一步动作。节点的主要协作方式，就是读取它并更新它。

当前项目把状态分成共享的执行字段和各领域自己的业务字段。共享字段包括当前 Agent、已经选择的技能、当前步骤、步骤历史、完成步骤和失败步骤。它们回答的是“现在谁在处理、处理到哪里、已经发生过什么”。

诊断还需要自己的字段，例如消息上下文、工具调用记录、工具返回、观察、证据、校验错误、调用轮次和最大轮次。这些内容不能因为追求统一，就全部挤到一个泛用字符串里。只有保留结构，程序才能判断是否取得新证据、是否还有查询预算。

顶层编排状态还会保存任务编号和追踪编号。任务编号帮助我们识别这一轮业务任务，追踪编号帮助我们关联这一轮执行链上的记录。设备身份和事件身份则帮助我们确认这些数据究竟属于哪台机器、哪一次故障。它们是不同用途的标识，不能随意互相替代。

举个例子，最开始的状态可能只有设备编号、报警和当前快照。诊断完成后，状态增加诊断结果；知识查询完成后，增加文档和证据；工程定位完成后，再增加部件归属和图纸记录。维修方案接收的是这份已经积累的信息，而不是重新猜测前面发生了什么。

节点一般返回自己负责更新的字段，而不是重造整份任务。顺序组合时，代码把已有状态与新字段合在一起，让后续操作看到更新后的资料。因此，一个查询节点增加观察，并不意味着它应该把已有设备编号、诊断证据或者错误记录清掉。

还有一个容易忽略的问题：声明状态字段，并不等于已经完成运行时校验。代码里的类型字典主要描述结构，很多字段还是可选的。真正检查输入、结果和业务条件的，是请求模型、领域验证器以及运行时门禁。不能因为状态类型里写了“证据”，就认为这条证据已经可信。

所以，理解状态时，我会连续问四个问题：这份数据从哪里来，属于哪个任务和设备，哪些字段经过了校验，下一步依据什么继续。只要这四个问题能够回答，节点之间的信息传递就比较清楚。否则，即使每个节点都返回了一大段文字，也不能证明整条流程有可靠的数据基础。

## 第五节：四层状态：执行成功不等于业务完成〔11:00–14:00〕

这里我要专门区分四种状态，因为很多显示不准确的问题，都来自把它们混在一起。第一种是执行记录状态，第二种是领域结果状态，第三种是业务对象状态，第四种是循环评估状态。它们可以同时存在，但回答的问题不一样。

执行记录状态回答的是：这次调用怎样了。当前执行管理器有待执行、执行中、成功、失败、超时、取消和未知这些类别。成功说明处理器完成了这次调用，失败说明发生了执行错误。超时表示等待超过限制，并不自动证明外部操作没有生效。

领域结果状态回答的是：这次专业处理得到了什么。诊断可能正常完成，也可能走降级路径。知识检索可能证据充足，也可能证据不足。工程查询可能找到了对应资料，也可能缺少工程数据。一次查询正常返回“没有足够证据”，并不一定是程序崩溃。

业务对象状态回答的是：工单、报告或者零件现在处于什么业务位置。创建工单成功，只说明有了工单记录；派工成功，只说明负责人安排好了；提交反馈成功，也不能直接说明设备已经恢复。它们不是同一个动作，所以不能共用一个笼统的“完成”。

再看质量检测。如果一次检测按要求取得测量数据，最后发现零件不合格，这可以是一次成功执行的检测，但业务结果是不合格。反过来，如果没有外观或材料数据，却得到一个“通过”，即使接口请求返回成功，也不能把零件判定为合格。

第四种是循环评估状态。运行时评估器会返回继续、重新规划、结束或者阻断。继续表示还有工作可以做；重新规划表示当前路径需要调整；结束表示当前评估目标已经满足；阻断表示当前不允许再向后推进。这些判断也不能直接等同于工单数据库里的完成状态。

特别要注意，一个领域的“结束”，不代表整个任务都结束了。诊断完成以后，外层仍可能需要知识、工程资料、维修方案和派工。当前运行时会保留这种区别，避免因为第一个 Agent 给出结果，就提前跳过剩下的计划。

此外，代码会记录步骤完成，但这个标记首先表示子操作返回了。它不自动代表业务验收通过。我们还要继续看校验结果、缺失信息、证据状态和停止原因。例如，一个验证节点完成执行以后，完全可能得出“验证不通过”。

所以，查看日志或页面时，不能只问“成功了吗”，而应该问“哪一层成功了”。我们至少要能区分：调用成功、证据成立、业务动作生效和整轮任务结束。只有这样，系统才不会把查到一条记录，误显示成整台设备已经修好。

## 第六节：诊断内部循环：推理、执行、观察、校验〔14:00–17:00〕

现在进入最典型的 Agent Loop：诊断内部循环。诊断图有七个节点，我按中文职责介绍：准备、推理、工具检查、执行并观察、循环检查、候选校验，以及结束。七个节点中有些可以被多次访问，这就是循环发生的位置。

准备阶段把事件整理成消息上下文，再选择诊断技能和工具范围。随后进入推理。模型面对当前上下文，可以提出继续查数据，也可以给出候选诊断。这里的模型响应还只是候选动作或候选结论，不是已经被执行的事实。

如果模型提出工具调用，先经过工具检查。检查会判断工具是否在当前允许范围内，以及参数是否符合要求。被拒绝的请求不会直接执行；拒绝信息会作为工具结果写回上下文，让下一次推理知道这个动作没有被允许，而不是假装工具已经查到资料。

通过检查以后，才进入执行并观察。执行部分保存工具名称、输入参数、实际返回、耗时和错误。观察部分把这些原始结果组织成可追踪的观察与证据，并放进消息上下文。因此，下次推理看到的是本轮新取得的数据，不是凭空获得了额外信息。

之后来到循环检查。如果还没有达到轮次上限，而且观察不是连续重复，流程可以回到推理。此时同一个推理节点再次执行，但它的输入已经不同：状态里增加了工具结果、证据，甚至增加了上一次动作被拒绝的原因。

如果模型给出候选诊断，流程进入候选校验。验证器检查结论结构、证据和置信度等内容。通过以后进入结束；没有通过，而且预算仍然允许，就把缺失或错误信息写回上下文，让模型继续补证据或修正输出。预算耗尽时则结束到回退路径。

这里的“循环”，就是这一条明确的回边：推理，检查动作，执行并观察，判断是否还能继续，再回到推理。另一条回边是候选校验没有通过以后，带着校验错误重新进入推理。它不是重复发送完全相同的提示词，也不是无限要求模型“再想一想”。

例如，第一次只知道有温度异常，模型可能先查报警定义和设备快照。第二次看到实际数据后，再决定是否需要历史趋势。如果返回没有提供新的观察，继续循环的意义就很小，程序会按现有守卫停止，而不是一直查询直到凑出确定答案。

这个过程说明，诊断的智能性并不只在模型回答中，还在于动作是否合法、观察有没有写回、证据是否进展，以及结论是否经过校验。少了其中任何一个环节，所谓 Agent Loop 就可能只剩下模型重复生成文字。

## 第七节：知识与 CAD 循环：不是所有循环都靠模型决策〔17:00–20:00〕

除了诊断，知识检索和 CAD 工程定位也有内部循环，但它们的循环方式更偏确定性。这里要明确一点：有循环不代表每次都由模型自由决定下一步。按任务类型建立查询队列，逐次执行并检查结果，同样可以构成有界的证据处理循环。

知识图有六个节点：准备、检索、查询细化、结果整理、验证和结束。准备节点内部完成输入归一化、技能选择、查询类型识别和检索计划。检索节点内部则同时执行一次检索和一次观察。合并以后，节点少了，但查询和观察都还保留。

知识状态里保存待执行工具、已经得到的文档、证据、调用次数和是否细化过查询。每一次检索从队列中取一个来源，取得返回，再判断需要的来源是否覆盖、队列是否还有任务、是否还有预算。满足条件才进入结果整理和验证，而不是只要命中第一条文档就立即宣布证据足够。

如果没有找到文档，而且仍有预算，系统可以细化查询，补充与报警、部件或知识类型有关的检索词，再查询一次。当前这条细化路径有标记约束，不是无限扩写问题。与此同时，已经明确指定文档或片段的查询，不应该为了增加结果数量而随意扩散。

这里要特别注意：结果整理节点虽然沿用重排这个名称，但当前图里的操作包括去重和证据构造。不能因为节点叫“重排”，就推断这里一定又调用了一次重排模型。判断实际模型调用，应当看工具链和模型服务的真实记录，而不是只看节点名字。

CAD 图有五个节点：准备、工程查询规划、查询、关系验证和结束。它根据问题属于物料清单、位置、装配关系还是普通部件查询，建立查询队列。每次查询执行一个工程工具，把部件、图纸、物料和关系等结果合并到状态，再回到规划节点判断是否还有下一项。

当队列耗尽或达到预算，CAD 进入关系验证，不再继续处理上一轮旧观察。验证会检查必要工程资料，并核对返回部件的设备归属。请求指定某台设备时，缺少归属或者归属不一致，都不能因为零件名字相似，就当成正确的定位依据。

因此，这两个循环的共同点是：查询动作有限，状态逐步积累，最后必须验证。区别是知识关注资料和来源覆盖，CAD 关注工程关系及设备归属。它们不像诊断那样以模型推理为核心，但同样承担“取得更多证据，然后决定是否继续”的任务。

## 第八节：顶层 Runtime Loop：选择并协调多个 Agent〔20:00–23:00〕

现在我们把视角从一个 Agent 内部，移到多个 Agent 之间。当前项目还有一层顶层 Runtime Loop，我下面称它为运行时循环。这层循环不是诊断图里多绕一圈，而是决定整轮任务接下来应该调用哪一种领域能力。

顶层 LangGraph 目前只注册一个运行时节点。这个节点把共享任务状态交给运行时协调器。并不是说整个系统只剩一个节点，而是说跨 Agent 的规划和执行控制，已经集中在运行时，而九个领域 Agent 仍然有各自的执行图。

入口先把用户请求或监控事件解析成目标、实体、约束和能力要求。对于自然语言请求，现有路由 Agent 会参与识别意图。然后 Planner，也就是规划器，把能力要求组织成动作计划。当前基础规划器是确定性的能力映射，它本身不调用模型，也不负责执行工具。

计划中的每一项都使用统一动作对象表达。动作会记录类型、目标、参数、理由，以及是否有副作用和幂等身份。系统能表达 Agent 动作、工具动作、重新规划、结束和等待；但默认异常计划中的具体业务处理主要以调用领域 Agent 的动作体现，不是每种类型都会在每轮出现。

协调器取出当前动作，通过分发器调用对应 Agent，再把结果写回共享状态。它会保留这个领域的输出、观察、证据、校验和轨迹，并推动计划位置。这样，下一项动作能够拿到已经生成的诊断、知识或工程资料，不用只靠一句摘要猜测前面的结果。

返回以后，领域评估器会判断这项结果是否足够，是否需要重新规划，或者应该阻断。知识证据仍然不足时，当前代码会阻断后续推进，不能把计划里还有“维修”和“工单”，误当成仍然可以安全执行这些动作的理由。

如果结果需要重新规划，协调器会依据缺失信息重新请求规划器，而不是直接执行 Agent 随口提出的建议。重新规划也有次数限制。新的动作仍然经过同样的分发和业务边界，不能因为进入第二轮，就放松权限、证据或维修必要性的要求。

这个顶层循环当前是协调器把单轮处理回调交给共用循环引擎执行。引擎也提供另一种更细分的接口，把观察、评估、选动作、执行和状态更新分别传入。讲架构时应当区分“当前正式入口采用的路径”和“引擎还提供的接口”，不能把所有接口都描述成同一次任务同时执行。

所以，我们可以用两层循环来概括：外层负责“下一项领域任务交给谁”，内层负责“这个领域是否还要继续取证”。外层有进展，不代表内层一定成功；内层完成，也不代表外层计划全部结束。它们通过结果、证据和状态协作，而不是互相替代。

## 第九节：循环的边界：停止、超时与重复副作用〔23:00–25:00〕

有了循环，还必须讨论停止。一个可靠的 Agent 不是永远执行下去，而是在信息足够时结束，在不允许继续时停止，在暂时无法完成时保留明确原因。停止不等于失败，继续也不一定意味着取得进展。

当前诊断有轮次和重复观察检查。知识和 CAD 也有查询预算。共用循环引擎另外提供最大迭代、超时、动作去重、证据进展和成本预算等守卫。不同调用路径启用的策略并不完全一样，因此不能说所有任务都使用同一个固定次数，也不能说声明了预算字段就一定配置了成本上限。

权限检查和业务门禁仍然有独立位置。循环守卫负责控制循环，不代替工具白名单，不代替派工审批，也不代替维修验收。特别是在不同引擎接口里，检查发生的顺序有区别，不能仅凭“用了循环引擎”，就认为所有副作用都自动得到了事前保护。

再看重复动作。查询一份手册和创建一个工单，风险不同。写操作需要正确的幂等身份，并且要核对动作和业务参数。不能因为上一轮已经有工单，就认为本轮更新、完成或关闭也自动执行了。

超时尤其需要谨慎。等待结束，不等于底层线程已经停止；外部系统可能已经提交写入，只是响应没有返回。因此，执行管理器会保留超时或副作用未知的信息。遇到这种情况，正确做法是查权威记录对账，而不是盲目再创建一次或再关闭一次。

这就是我们给循环加边界的原因：既避免没有新信息时一直消耗资源，也避免因为重复调用，让实际业务记录发生重复变化。Agent 的目标不是“总要输出成功”，而是清楚说明完成了什么、缺少什么，以及为什么停在这里。

## 第十节：贯穿例子：一台设备异常后的状态变化〔25:00–27:00〕

我用一个教学例子，把节点、状态和循环连起来。假设监控取得某台设备的异常事件，事件带有设备身份、报警信息、采样时间和当前快照。这里不假定任何工业温度阈值，也不预先断言是哪个零件损坏。

事件进入顶层后，产生本轮任务与追踪身份，再形成需要的能力计划。诊断阶段先读取已有信息，根据需要调用工具。工具结果写进观察以后，诊断可以再次推理。最终得到的应该是带证据和可信度信息的候选判断，而不是只有一段维修建议。

随后，知识阶段查询与当前问题有关的文档和操作依据，工程阶段查询对应设备的部件和图纸记录。它们分别用自己的有界循环积累证据。无资料或归属不符时，返回不足状态；不能为了把流程走完，就填入其他设备的资料。

维修方案阶段拿到诊断、知识和工程上下文，整理分析、维修步骤、工具和备件，再经过安全与方案检查。是否需要维修，以及资料是否足以派工，都是业务判断，不是每一次监控波动都应该自动产生工单。

前置条件满足以后，工单阶段才处理创建和人员安排。到这里，自动执行的一段计划可以完成，但维修任务通常仍在等待人员执行。我们不能把“已派工”写成“已修复”，也不能让循环一直阻塞着等维修人员在现场操作结束。

后续维修反馈、可信恢复验证、合法关闭、报告和经验保存，会在对应业务入口继续推进。前后记录需要关联到同一故障和工单。整个故障生命周期可以跨多次运行，不等于必须由一个不断运行的模型调用撑到最后。这也是日志应按业务任务组织，而不把每次采样都当成完整故障任务的原因。

## 第十一节：没有内部循环的 Agent，怎样完成任务〔27:00–29:00〕

最后，我解释一个常见问题：没有内部循环的 Agent，是不是就不算 Agent，或者是不是不能完成任务。答案是否定的。需要循环的是反复取证和调整决策的任务；输入明确、动作明确的业务处理，更适合有限的流程和分支。

维修方案图的六个阶段是准备、上下文收集、方案构建、安全检查、方案验证和结束。虽然内部不注册循环回边，但方案结果会交给外层评估。需要补资料或重新规划时，由运行时协调，而不是要求维修方案自己无限生成。

工单图有七个节点。创建路径先检查条件，再创建工单、收集派工上下文、选择人员、执行派工，最后校验结果。查询、反馈等已有工单动作，则进入另一条执行分支。两条路径共用部分节点，但不是每次都走全部七个，也不是每次都创建新工单。

质量图有五个节点，其中检测阶段内部顺序执行尺寸、外观、材料、功能和工艺检测。五个图节点不代表只检测五次接口，更不代表可以漏掉某类证据。整改和复检是后续业务状态迁移，不是让模型在同一次调用里不停修改判定直到通过。

报告图有五个节点，负责准备、收集上下文、组织正文、按请求保存和结束。记忆图有七个节点，检索与学习是不同分支；学习之前需要符合准入要求。经验保存和报告保存有真实副作用，不能当成普通生成文字来无限重试。

因此，当前架构是混合的：部分领域图有内部循环，部分领域图用有限流程完成一次操作，外层运行时再协调这些领域能力。我们评估它是不是合理的 Agent 系统，要看职责、状态、工具、验证和控制边界，而不是要求每一类 Agent 都写一个循环。

## 第十二节：结尾：用三句话记住整个架构〔29:00–30:00〕

今天的讲解可以收束成三句话。第一，节点是执行阶段，不是模型数量；合并节点可以减少调度，但不能删除真实操作和重要门禁。第二，状态是贯穿任务的结构化资料，不只是页面上的一个状态标签；输入、观察、证据、校验和业务结果都需要保留清楚的关系。

第三，Agent Loop 是取得新信息后再次判断的有界循环，不是无限重复调用模型。当前既有诊断、知识和 CAD 的内部循环，也有跨 Agent 的顶层运行时循环。它们必须清楚地回答什么时候继续、什么时候调整计划、什么时候结束和为什么阻断。

最后再强调一个底线：程序执行成功，不代表设备已经修复；模型认为可信，不代表工业验收通过。只有把节点职责、状态含义、真实证据和停止条件连在一起，系统才是一个可解释、可检查的任务执行系统。我的讲解到这里，谢谢大家。
