## 主要原因

1. **日志同步写入且每条重新建立数据库连接。** `TraceRecorder.record` 同步调用 `MySQLTraceStore.append`，每次经 `mysql_session` 新建连接。正常配置下三次只读 `SELECT 1` 测量：新建连接中位数 768.575 毫秒，已建立连接上的查询中位数 2.191 毫秒。实际 Trace 内初始化、读取 Skill 等本地步骤也存在约 0.3—0.8 秒间隔。测量没有写业务数据，也没有测量 INSERT 的实际时间，不能把所有剩余耗时都归给数据库。
2. **模型连接异常引发降级和后续复诊。** 初次诊断两段 reason 窗口为 4.210 和 2.629 秒，第二段明确报 `URLError: tls_failure`。这是当前事件的真实错误，不是等待满 90 秒。降级路径还再次读取了已经成功获取的同一报警定义。
3. **知识检索包含额外模型回答。** 当前服务日志中两次检索总耗时分别为 12.955 秒和 12.111 秒，其中回答生成分别耗时 10.676 秒和 9.626 秒。向量和重排请求同时出现 HTTP 503，流程使用已有降级路径继续补充证据。
4. **页面有独立的旧响应覆盖竞态。** 全局每秒轮询快照，慢的旧 running 响应可能覆盖较新的 completed 响应。隔离浏览器已复现。当前实际诊断视图能够显示 completed 正文和“后续流程仍在处理”；fallback 的状态字典另外缺少中文标签。这个竞态不能解释后台实际耗时，但会放大等待感。

## 修改重点与边界

优先复用日志写入连接，同时保留每条记录独立事务、失败不重放、审计可见性；然后减少取证过程中不必要的模型回答与已知工具选择往返，并保护快照轮询免受旧回包覆盖。不能用降低证据门槛、延长页面超时或提前宣称诊断成功替代这些优化。
